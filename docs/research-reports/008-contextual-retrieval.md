## 1. Executive Summary

Anthropic's Contextual Retrieval is a **preprocessing technique** that prepends chunk-specific explanatory context to each text chunk before it is embedded and before a lexical (BM25) index is built. The key insight: traditional RAG destroys context by splitting documents into chunks, so individual chunks become semantically ambiguous (e.g., *"The company's revenue grew by 3% over the previous quarter"* loses its referent). By asking an LLM to generate a 50–100 token situating preamble for each chunk, retrieval accuracy improves dramatically.

Reported results (top-20-chunk retrieval, averaged across codebases, fiction, ArXiv papers, and science papers):

| Technique | Failure rate (1 − recall@20) | Relative reduction |
|---|---|---|
| Baseline (embeddings only) | 5.7% | — |
| + Contextual Embeddings | 3.7% | −35% |
| + Contextual Embeddings & Contextual BM25 | 2.9% | −49% |
| + Reranking (Cohere) | 1.9% | −67% |

The technique is inexpensive (≈ $1.02 per million document tokens using prompt caching) and uses a single reusable prompt — no per-domain tuning required to realize most of the gain.

## 2. Background: The Context Conundrum

Traditional RAG pipelines follow a fixed sequence:

1. Split the corpus into chunks (usually a few hundred tokens)
2. Embed each chunk with an embedding model
3. Store embeddings in a vector database for similarity search

At query time, the top chunks are retrieved and appended to the prompt. The problem: **splitting destroys context.** A chunk like *"The company's revenue grew by 3% over the previous quarter"* is unusable both for retrieval (the embedding lacks the referent "ACME Corp, Q2 2023") and for generation (the model can't know which company or period is meant).

This is the direct analog of a challenge in job-postings retrieval: a job description chunk containing only *"Experience with transformers, attention, and RNN architectures"* loses which role and seniority level it belongs to, degrading both retrieval and downstream interpretation.

---

## 3. The Core Technique: Contextual Embeddings & Contextual BM25

Contextual Retrieval fixes the context loss by **prepending a chunk-specific situating preamble** to each chunk *before* both embedding and BM25 indexing. The transformed chunk is used for both the dense vector and the lexical index, so the two sub-techniques are:

- **Contextual Embeddings** — the contextualized chunk is embedded, so the dense vector now encodes the chunk's relationship to the whole document.
- **Contextual BM25** — the contextualized chunk is indexed lexically, so exact-match queries (e.g., unique identifiers like "TS-999") that pure embeddings miss can still hit the right chunk.

Example transformation:

```
original_chunk = "The company's revenue grew by 3% over the previous quarter."

contextualized_chunk = "This chunk is from an SEC filing on ACME corp's performance in Q2 2023; the previous quarter's revenue was $314 million. The company's revenue grew by 3% over the previous quarter."
```

Anthropic explicitly notes that earlier context-augmentation approaches were evaluated and found weaker:

- **Generic document summaries prepended to chunks** — "very limited gains"
- **Hypothetical document embedding (HyDE)** — evaluated, low performance
- **Summary-based indexing (LlamaIndex Document Summary Index)** — evaluated, low performance

The distinguishing feature of Contextual Retrieval is that the preamble is **chunk-specific** (situating this chunk in the whole document), not a generic document-level summary.

## 4. The Contextualizer Prompt

The contextual text is generated by an LLM using a single reusable prompt (Claude 3 Haiku in the original experiments):

```
<document>
{{WHOLE_DOCUMENT}}
</document>
Here is the chunk we want to situate within the whole document
<chunk>
{{CHUNK_CONTENT}}
</chunk>
Please give a short succinct context to situate this chunk within the overall document for the purposes of improving search retrieval of the chunk. Answer only with the succinct context and nothing else.
```

The resulting preamble is typically **50–100 tokens**, prepended to the chunk before embedding and before BM25 indexing.

## 5. Cost Model & Prompt Caching

Contextualizing millions of chunks manually is infeasible; the LLM does it cheaply. The cost is dominated by passing the whole document alongside each chunk — which is where **prompt caching** matters: the document is loaded into the cache once, then referenced across all its chunks, avoiding re-sending the full document per chunk.

Anthropic's worked cost model (800-token chunks, 8k-token documents, 50-token context instructions, 100 tokens of context per chunk) yields a **one-time cost of $1.02 per million document tokens** to generate contextualized chunks.

## 6. Performance Results

Experiments spanned multiple knowledge domains (codebases, fiction, ArXiv papers, science papers), embedding models, retrieval strategies, and evaluation metrics. Metrics use **1 − recall@20** (percentage of relevant documents failing to be retrieved in the top 20 chunks), with the top-performing embedding configuration (Gemini Text 004).

- **Contextual Embeddings** reduced failure rate **35%** (5.7% → 3.7%)
- **Contextual Embeddings + Contextual BM25** reduced failure rate **49%** (5.7% → 2.9%)

Anthropic reports the improvement held **across every embedding-source combination evaluated**.

---

## 7. Reranking Layer

Adding a reranking step on top of Contextual Retrieval yields further gains. Reranking filters the (often hundreds of) chunks returned by initial retrieval down to the most relevant before passing them to the model:

1. Initial retrieval returns top-150 potentially relevant chunks
2. Top-N chunks + query are passed to a reranking model (Cohere Rerank in their tests)
3. Reranker scores each chunk by relevance to the prompt
4. Top-K chunks (top 20) are passed to the generation model

Result: **Reranked Contextual Embedding + Contextual BM25 reduced failure rate 67%** (5.7% → 1.9%). Trade-off: reranking adds runtime latency (though the reranker scores chunks in parallel) and a cost/latency vs. quality trade on how many chunks to rerank.

## 8. Implementation Considerations

Anthropic flags five factors that affect results:

1. **Chunk boundaries** — chunk size, boundary placement, and overlap affect retrieval performance
2. **Embedding model** — improvement holds across all models, but Voyage and Gemini embeddings were most effective
3. **Custom contextualizer prompts** — domain-specific prompts (e.g., injecting a glossary of cross-document key terms) may outperform the generic prompt
4. **Number of chunks** — 20 chunks beat 10 and 5; more chunks raise recall but can distract the model
5. **Always run evals** — passing the contextualized chunk may require distinguishing context from chunk content downstream

## 9. Relevance to This Project

Contextual Retrieval is directly applicable to the Semantic Career Mapping Platform's embedding pipeline, and the project's own research has already converged on adjacent ideas:

- **Hybrid retrieval (BM25 + dense)** is already a recognized technique in this project (`research-reports/001`, §7 "Hybrid Retrieval (BM25 + Dense)"; `technical/tech-choices.md` lists hybrid BM25 among alternatives considered). Contextual Retrieval strengthens the case and specifies *how* to build the BM25 side effectively.
- **Job-postings share the context problem** — a chunk that is only skills text loses the role, seniority, and company referents. A chunk-specific preamble generated from the full posting would restore that context for both dense and lexical retrieval.
- **Section weighting / skill extraction** (existing feature-engineering plans in `technical/embedding-pipeline.md`) could be complemented by a contextual preamble that names the role and section provenance.
- **LLM-based cleaning** already exists in the pipeline (gpt-5.4-nano for boilerplate removal), so an LLM contextualizer step is a natural, low-friction extension rather than a new dependency class.
- **Reranking** and **recall@K / precision@K / NDCG** evaluation are already on the project's IR-metrics roadmap (`technical/evaluation.md`), so the evaluation harness this technique assumes is planned.

A low-cost experiment would: (1) generate a situating preamble per chunk from each full posting, (2) prepend it before embedding and BM25 indexing, and (3) measure the change in the existing self-retrieval and separation-gap proxy metrics.
