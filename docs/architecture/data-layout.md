# Data Layout & Object Storage Naming

Data lake-style ingestion mechanisms and S3-compatible object store conventions are used as the project migrates towards cloud deployment and productionization. 

A single bucket is used for now (until scope justifies expansion into separate buckets), as well as a structured key builder and metadata object for provenance and relational querying later down the line. 

## 1. Buckets

Data Data is organized into three top-level containers -- two domain branches plus one shared metadata branch. 
The `eval`/`live` split separates the evaluation set from the live data. 
Data lives in a single S3-compatible bucket until scope expands to justify separate ones. 

| Bucket | Contents | Mutability |
|---|---|---|
| `eval/` | Human ground truth — grades LLM output against author intent | Authored, versioned, never regenerated |
| `live/` | Raw data + derived artifacts | Regenerable |
| `configs/` | Config manifest — hash -> generation parameters, shared by eval and live | Append-only |

```
live/
  raw/<id>/
    source.md           # raw job descriptions (verbatim source)
    metadata.json       # e.g. employer, date of addition, etc.
  derived/<id>/
    <variant>/v1.json   # e.g. cleaned data, engineered features, etc.
  embeddings/
    <model>/            # group embeddings by the same model
        <variant>/v1/<id>.npy

eval/
  postings/<id>/
    text/v1.json        # manually-cleaned
    <variant>/v1.json   # e.g. engineered features, labels, etc. 
  _current.json         # current eval set version

configs/
  <config-hash>.json    # e.g. model used, temperature, system prompt, etc.
```

Here `<id>` is the UUIDv7 posting id (see §2.1), `<variant>` is a derived-artifact
name (e.g. `clean-text`, `llm-clean-text`, `labels`), `<model>` is an embedding
model name, and `<config-hash>` is a 64-char lowercase hex SHA-256 (§2.3).
Every segment is lowercase: `<id>` is a lowercase UUIDv7 (`[0-9a-f-]`), so the
former "uppercase allowed in `<id>`" exception no longer exists.

## 2. Object Keys

Keys are generated on ingestion by a structured key builder [`keys.py`](../../backend/storage/keys.py). 
The key structure inside `live` attempts to capture the dimensions by which we anticipate to query and uniquely identify data.  
Additional metadata is stored elsewhere for provenance. 

### 2.1 Category

`<category>` reflects the largest dimension; this can be the `raw` data, `derived` artifacts, or vector `embeddings`. 
The pipeline transforms `raw` data into various `derived` artifacts, before producing `embeddings` used for semantic comparison. 

### 2.2 Object `id`

The object `<id>` is a globally unique entity key for each data object. 
Refers to a single job posting across transformations.
It is generated as a time-ordered `UUIDv7` string (stored identically in `metadata.json` alongside additional information).

### 2.3 Variants

The `<variants>` key reflects artifacts generated by various transformations of the raw data. 
Examples include cleaned text, engineered features, and custom labels. 
`<variants>` acts as a dimension to separate these approaches over arbitrary data. 

### 2.4 Versions

Similarly, the `<versions>` key reflects artifacts generated by different versions of the same transformation variant. 
Data science and ML engineering is an iterative process, and we should store artifacts from each iteration separately. 

### A.1 Metadata

Other information is important for data provenance, specifically the `metadata.json` associated with each job posting. 
This may eventually expand into an Athena SQL database useful for relational querying over the data.

## 3. Configuration

MLflow for experiment tracking and versioning is planned. 
In the meantime, settings configuration for each pipeline version should be tracked somewhere, to set up the eventual migration.

The top-level `configs/` key will store this information, for example the LLM used and at what temperature, the system prompt, or the embedding model, or the clustering model and relevant parameters.

### 4.1 Deduplication

Dedup is deferred and observable for now, preferring to focus on schema-on-write principles and data lake-style ingestion.

Current plans are to alarm the user for ingestion of identical data entries, with respect to the employer and job title metadata. 

A more sophisticated semantic-similarity filtering tool may eventually be designed to catch cases where the same job posting is collected twice, but posted on different dates, or ingested differently that wouldn't be caught by a naive content hash (such as a trailing space).
