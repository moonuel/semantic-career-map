# Design — Embedding Pipeline

Architecture, decisions, and risk notes for the change. Spec deltas live in `specs/embedding-pipeline/spec.md`; this file records the reasoning behind them.

## Decisions (user-approved 2026-10-26)

1. **Cache granularity — SQL anti-join (row-level), mirroring `select_uncleaned`.** Selection = cleaned artifact rows for the pinned input version anti-joined against produced embedding rows on `(source_hash, configuration_hash)`: only postings with no embedding row under the run's configuration are embedded — the continuously-ingesting lake embeds deltas, never the corpus. The dataset-level short-circuit collapses into the degenerate case: an anti-join returning zero rows is the healthy no-op run (the cleaning tier's day-2 idempotence artifact). A configuration change still re-embeds deliberately — that lands under a new `version=` prefix as a new generation, not drift. Note on the withdrawn objection: the earlier design priced a Python-side row-level lookup ("full existing-parts scan for near-zero reuse value"); the SQL-side anti-join never performs that scan — its cost-bearing side is the tiny embeddings Parquet partition, server-side pruned, exactly as `artifacts_cleaned` is the tiny side for cleaning.
2. **`model_version` — config-pinned revision string, asserted at load.** The configuration carries `model_revision` (e.g. the HF revision hash of `sentence-transformers/all-MiniLM-L6-v2` the run intends); the encoder resolves the actually-loaded revision and fails fast on mismatch. Ambient resolution (whatever HF hands back) is banned from provenance — a silently-moved default revision would fork the vector space invisibly.
3. **SQL text storage — verbatim in `configs/<sha256>.json`.** The configuration object contains the full SQL text; its canonical serialization is hashed; the object is stored at `keys.config(hash)`. Manifests and rows carry only the hash — no keyspace pollution (data.md §5 config-object discipline), and any dataset resolves to the exact SQL text that selected it.
4. **One openspec change, four layers as task groups.** Spec deltas stay coherent as one capability name; layer boundaries become checkpoint gates (user review between layers).
5. **AWS deployment — ECS Fargate scheduled task (2026-10-26, validate-early).** Clone the cleaning tier's deployment shape: `task-definition-embed.json`, ECR image with the model baked in (cold-start-free, network-independent of a hub pull at task start), same task-env IAM contract, EventBridge cadence mirroring the clean job's. SageMaker stays out of scope — idle-billed endpoints are the anti-pattern for a scheduled batch, and batch-transform outputs would need lake-provenance re-shaping back into manifests/checkpoints/configuration rows. The validation effort lands at the END of Layer 3 (after recovery + concurrent-run hardening) so the deployed container validates the final reliability surface once. The `EmbeddingEncoder.encode(texts) -> float32` seam is the endpoint-swappable point if the retrieval-time query embedding ever decouples from the FastAPI process; at present, in-process encode there is the likelier correct shape.

## Layering rationale (feature-plan)

The risk is the integration seam — Athena runner lifecyle × model load × S3 write — not the pure functions. So Layer 1 is a throwaway spike (`scripts/embed_spike.py`) proving the whole seam with hardcoded inputs before any durable code exists. Layer 2 harvests only what the spike run used. Hardening (Layer 3) is bounded by the two reliable sources of evidence: what the spike exercised, and the `cleaned-artifacts` durability conventions this repo already adopted (checkpoint/flush discipline is repo policy, applied by override rather than spike evidence). Observability (Layer 4) adds manifest/accounting surfaces plus named log points, each answering a specific future question.

## Key shape (fixed by data.md §7)

```
lake/embeddings/model=<model>/variant=<variant>/version=<vN>/part-<run-id>-<seq>.parquet
```

- `model` partition: lowercased, slash-free segment of the model family (spike uses `all-minilm-l6-v2`); the full HF id rides in each row's `model` column, so partition name stays a prefixed grouping, not an identity claim.
- Rows: `source_hash, embedding, model, model_version, input_artifact, input_version, embedding_dimension, normalization, created_at` + `configuration_hash`, `run_id` (row-level provenance lives in the data too — not reconstructible only via manifests).
- One `<id>.npy` per posting is legacy (`live/`); the Parquet dataset is the authoritative representation; any index is rebuildable (data.md §7).

## Risk notes

- **Athena cost/scan:** the anti-join reads the registered embeddings location (Parquet-compact, one pinned generation) against the artifacts side — the raw JSON lake is deliberately not in this query. As-built correction (Layer 2): Hive partition columns live in the pinned location, not the payload, so the query filters the payload cache identity (`configuration_hash`) only; the generation scope is the registration's job. The adapter bounds rows deterministically (deployment bound).
- **Concurrent-run idempotence (learned live):** two runs sharing a configuration can race the anti-join and both encode+commit the same postings — duplicates across parts with distinct `run_id`s (observed during Layer 2: three orphaned processes re-encoded the same 4,442-row delta into a shared version prefix; fixed by pruning zombie parts, canonical run retained). **As-built (Layer 3, task 3.2):** part-level reconcile chosen over a run-claim lease — a lease needs store-atomic create-if-absent (not on the ObjectStore surface, unproven on Garage) plus TTL expiry machinery; reconcile needs only put/get/list + delete (added to the store for this, S3-idempotent) and heals even out-of-band states like the orphan incident. `backend/pipeline/embedding/reconcile.py::reconcile_configuration` runs before every selection: it groups the version prefix's parts by their minting run (the run id rides in the part leaf), keeps one canonical copy per `(source_hash, configuration_hash)` from the earliest run (UUIDv7 ids compare chronologically), deletes fully-duplicate parts, and rewrites partially-duplicate ones row-for-row (schema + provenance preserved). **Deliberate immutability deviation:** the lake is append-only, but duplicate rows are a defect state — same call the manual prune made. **In-flight guard:** runs whose parts' `created_at` are younger than 6h are deferred untouched (pruning a live writer's parts would strand its manifest); the consequence is duplicates of an *in-flight* racer heal on a later run, not the current one — eventual healing, no deadlocks, no clock synchronization. **Known wrinkle (for the checkpoint-print task):** the dataset manifest is one addressed object per dataset id, so concurrent same-config runs overwrite it (latest run's view survives); the flush-checkpoint layer's per-run manifests are where per-run accounting resolves this.
- **Query-side registration dependency:** the anti-join can only see produced vectors through the `postings_embeddings` registration. Provisioning rides the `provision_query_layer` pattern: no registration → no cache visibility → silent re-encodes.
- **Vector typing:** Parquet `list<float32>` for this change; a fixed-size-list migration (nice for downstream index builds) is additive later — versions add, they never get rewritten.
- **Writer reuse (as-built, task 3.3):** shared extracted = the key builders (`keys.embedding_part` / `keys.manifest_run_checkpoint`), the trigger vocabulary (rows/bytes/dwell/drained/stop), single-seq numbering, and the part → checkpoint commit-order invariant; the skeleton extraction itself was priced and rejected as adapter ceremony — the shared bookkeeping is ~25 lines behind 5–6 injected hooks while the stage payloads diverge completely (cleaning carries per-row LLM latency/usage/cost + per-row schema validation; embedding carries one float32 matrix per encode batch and a run-scoped `created_at`). `backend/pipeline/embedding/writer.py` is the stage-native sibling, same protocol (`add_batch`/`maybe_flush`/`flush_final`), and the buffer decouples part size from encode batch size (defaults mirror cleaning: 128 rows, 60 s dwell, 2 MiB). Drift of the shared invariants is guarded by the lake shape pinners plus the two stages' pinned order/shape tests rather than by a shared base class.
- **Checkpoint books must never dangle (as-built, task 3.4):** a part's flush checkpoint follows its content everywhere — the writer writes it strictly after the part; `reconcile_configuration` deletes a fully-duplicate part's checkpoint with the part and rebuilds a rewritten part's checkpoint (`trigger=reconciled`, `reconciled: true`, batch telemetry `None`) from the surviving rows; orphan parts (crash between the two puts — the only place books can lag rows) back-fill from part contents on the next run via `heal_orphan_checkpoints` (`trigger=recovered`, `recovered: true` — the cleaning stage's exact recovery shape, stage-native builder; rows are durable either way). The healing pass defers runs younger than the same 6h in-flight guard: racing a live writer's bookkeeping could overwrite its real checkpoint with a `recovered` mislabel, and the deferral costs nothing (rows stay durable; selection is unaffected by books; a crashed run older than the guard heals on the very next run).
- **Failure ledger:** cleaning's failure-ledger concept maps to embedding QA gate failures, not LLM failures — a posting with no usable text is a counted event, never a silent drop.
